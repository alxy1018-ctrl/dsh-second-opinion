# 评审方契约（reviewer contract）

这份文档定义**送出去什么、要回来什么**。它和"用什么方式送"是两件事：

| | 是什么 | 在哪定义 |
|---|---|---|
| **契约** | 输入字段、输出字段、成败语义 | 本文件 |
| **接入方式** | 子代理 / HTTP / 本地命令 / 不设 | `README.md` 的配置章节 |

所以你可以用任何语言、任何形态实现一个评审方——只要它满足这份契约，
插件不需要知道它是谁。**插件进程本身从不发起调用**，它只把"该怎么叫"写进技能正文。

---

## 一、输入（评审方收到的）

一个 JSON 对象：

```json
{
  "contract": "second-opinion/review@1",
  "stage": "requirement",
  "request": "用户的原始要求（原文，不要转述）",
  "analysis": "我方写出的分析",
  "artifact": "要评的东西：diff / 验证记录 / 契约 + 文件路径",
  "notes": "额外约束，可选"
}
```

| 字段 | 必填 | 含义 |
|---|---|---|
| `contract` | 否 | 契约版本标记。适配器可以用来判断自己认不认识这份载荷 |
| `stage` | 是 | `requirement` / `code` / `test` / `crosscheck` 之一 |
| `request` | 是 | 用户要求的**原文**。转述过的要求会让评审方审错东西 |
| `analysis` | 视阶段 | `requirement` 与 `crosscheck` 阶段是"我方的分析"，其余阶段可缺省 |
| `artifact` | 视阶段 | 要评的产出。**只放关键片段**（diff 的 hunk、改动的函数、失败现象），不要塞整份对话 |
| `notes` | 否 | 额外约束，例如"这个仓库禁止新增依赖" |

四个阶段想问的问题不一样，提示词模板在技能正文的 §3.4——
那边的措辞是给"人"看的，你实现适配器时可以直接抄，也可以自己写。

---

## 二、输出（评审方要给的）

**推荐文本形式**（适配器不用解析，调用方也好合并）：

```
[第二意见 · <一句话总体判断>]
发现：
  - <具体问题>
待澄清：
  - <需要向用户澄清的问题>
```

`发现` 与 `待澄清` 两节没有内容就整节省略（不要为了凑数硬写）。

**也接受 JSON**：

```json
{ "verdict": "一句话判断", "findings": ["具体问题"], "questions": ["要澄清的问题"] }
```

两种都行，调用方按内容读，不按格式读。

---

## 三、成败语义

**这是契约里最要紧的一段。** 评审是"锦上添花"，不是"必经关卡"：
拿不到评审时，调用方会照自己的分析继续干，然后如实告诉用户原因。

| 情形 | 怎么表达 | 调用方怎么做 |
|---|---|---|
| 拿到了评审 | 退出码 `0` / HTTP `2xx`，stdout 有内容 | 读它、合并 |
| 没拿到 | 退出码非 `0` / HTTP 非 `2xx`，**原因写到 stderr** | **不卡住**：继续干 + 一句话说明原因 |
| 超时 | 同上，原因写清楚是超时 | 同上 |

由此推出两条实现要求：

1. **失败要说人话。** 把 HTTP 状态、错误码、原始响应前 300 字符打到 stderr——
   调用方要拿这句话去告诉用户"为什么这次没有第二意见"。
2. **不要把失败包装成空评审。** 返回一段空文本或"（无问题）"，调用方无法区分
   "评审方认为没问题"和"评审方根本没说话"——这是最坑人的一种失败。

> 参考实现里已经这么做了：`adapters/exec.mjs` 把"退出码 0 但输出为空"**直接判成失败**
> （对外退出码 1，并在 stderr 说明原因）；`adapters/http.mjs` 会在载荷声明的 `contract`
> 版本对不上时提醒一句，但仍然照发——静默按老版本解释载荷是最难查的一类问题。

## 四、自己写一个适配器

三件事：**读 stdin → 干活 → 把评审打到 stdout**。

最小骨架（任何语言都行，这是 Node 版）：

```js
const chunks = [];
for await (const chunk of process.stdin) chunks.push(chunk);
const payload = JSON.parse(Buffer.concat(chunks).toString('utf8'));

// 你的评审方在这里被叫起来：调模型、查规则库、问另一个 agent……随你
const review = await askMyReviewer(payload);

process.stdout.write(review + '\n');   // 评审文本 → stdout
process.exit(0);                       // 成功
// 失败时：process.stderr.write(原因 + '\n'); process.exit(1);
```

本包自带两个参考实现，可以直接抄：

| 文件 | 演示什么 |
|---|---|
| [`adapters/http.mjs`](../adapters/http.mjs) | 接一个 OpenAI 兼容端点：参数解析、密钥只从环境变量读、超时、错误上报 |
| [`adapters/exec.mjs`](../adapters/exec.mjs) | 把契约转给任意本地命令，退出码原样传递 |

接好之后，在配置里把它挂上：

```yaml
reviewer:
  kind: command
  command: node /path/to/my-reviewer.mjs --json
  label: 我们组的规则库
```

或者如果你写的是 HTTP 形态，用 `kind: http` 少绕一层。

## 五、几条不要做的事

- **不要把密钥写进配置、命令行参数或 URL。** 密钥只从环境变量读——命令行会被打印进
  错误信息与会话日志，这是有过真实事故的。
- **不要只跑 happy path。** 评审方超时、端点 500、命令不存在，这三种是最常见的真实情况，
  适配器要能说清楚是哪种。
- **不要把整个仓库喂进去。** 载荷大 → 慢 → 贵 → 评审质量反而下降。给路径，让评审方自己读。
- **不要让评审方执行动作。** 它只出意见。改代码、跑测试、提交，都是调用方的事。
